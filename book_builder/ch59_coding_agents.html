1. The ReAct (Reasoning + Acting) Paradigm

How does an AI model transform from a conversational chatbot into an autonomous software engineer capable of resolving complex GitHub pull requests (such as Devin, SWE-agent, or Claude Code)?

Pioneered by Shunyu Yao et al. (Princeton, 2022), the ReAct (Reasoning + Acting) architecture enforces a strict cyclic triad:

$$\text{Thought} \to \text{Action} \to \text{Observation} \to \text{Thought} \dots$$
  1. Thought (Inner Monologue): The agent analyzes current state, reasons about the goal, diagnoses compiler errors, and formulates a falsifiable technical hypothesis.
  2. Action (Tool Call): The agent emits a structured tool execution request (e.g. view_file(path, line_range) or run_command("pytest tests/test_auth.py")).
  3. Observation (Environment Feedback): The runtime executes the tool and injects the raw terminal output, compiler stderr, or file contents directly back into the agent's context window.

2. Tool Architecture: Why Surgical Diffs Dominate

Early coding bots attempted to edit code by rewriting the entire file from line 1 to line 2,000. This is an engineering catastrophe:

  • Token Wastage & High Latency: Generating 2,000 lines of unchanged code consumes 4,000 output tokens, taking 30 seconds and costing $\$0.06$ per single-line edit!
  • Hallucinatory Truncation: In long files, LLMs frequently omit intermediate functions (e.g. emitting comments like # ... rest of code unchanged ...), corrupting the user's repository!

Production engineering agents use Surgical Diff Replacements:

replace_file_content(
    TargetFile="app/services/billing.py",
    StartLine=45,
    EndLine=55,
    TargetContent="discount = amount * 0.10",
    ReplacementContent="discount = min(amount * 0.10, max_cap)"
)

The agent outputs only the precise 5 lines being modified, slashing latency by 95% and preserving 100% of the surrounding codebase.

3. The Self-Healing Test-Driven Debug Cycle

A true software engineering agent does not guess whether its code works; it verifies it empirically:

  1. Reproduce: The agent writes a standalone reproduction unit test capturing the reported bug and runs it via terminal tool. The test must fail (Red).
  2. Localize: Using grep_search and stack trace inspection, the agent isolates the exact culprit function.
  3. Patch: The agent applies a surgical edit.
  4. Validate (Green): The agent re-runs the reproduction test. If it passes, it executes the entire repository regression test suite to guarantee zero side-effects.
  5. Self-Heal: If the test fails with a new traceback, the agent reads the exception in the Observation, reasons through the failure mode, and iterates!

FAANG & Tier-1 AI Interview Problems — Autonomous Agents

Problem 5.9.1 Hard OpenAI Anthropic

QUESTION: You are designing the context window management policy for an autonomous coding agent resolving an issue in a repository with $500,000$ lines of code across $2,000$ files.

  1. Why can you NOT simply concatenate the entire codebase into an extended context window (e.g. 1 Million tokens)?
  2. Design the Memory Compaction & Windowing Strategy that allows the agent to run for 100 execution steps without blowing past token limits or suffering attention degradation.
✓ Complete Step-by-Step Architectural Solution

Step 1: Why Megatoken Contexts Fail on Repositories:

  1. Cost & Latency: Ingesting 500,000 lines ($~2,000,000$ tokens) costs $\$10.00+$ per single step. A 30-step debugging session would cost $\$300.00$ and require 45 seconds of Time-To-First-Token (TTFT) per call!
  2. Needle-in-a-Haystack Degradation: Drowning the model in 2,000 irrelevant files causes severe attention dilution. The model loses focus on the 2 specific lines causing the bug.

Step 2: Production Context Management Strategy:

  1. On-Demand Windowed File Exploration: The agent starts with zero files loaded. It navigates using directory listings (list_dir) and regex search (grep_search), reading only the specific lines of interest (view_file(StartLine, EndLine)).
  2. Observation Pruning: Long terminal command outputs (e.g. 5,000 lines of test output) are truncated to the top 20 lines and bottom 50 lines (where the actual assertion failure resides).
  3. Rolling Memory & Task Summarization: When total conversation history reaches 70% of context capacity, an asynchronous background LLM call generates an executive summary of completed steps, key hypotheses tested, and verified facts. Old detailed tool observations are pruned, while the compact summary is prepended to the active scratchpad!
This keeps active context consistently under 32k tokens, enabling hours of continuous agentic work at minimal cost.

import re

class MockCodingEnvironment:
    def __init__(self):
        self.code_file = "def add_tax(price):\n    return price + 10 # BUG: Should be percentage!"
        self.test_file = "assert add_tax(100) == 110\nassert add_tax(200) == 220" # Expecting 10%

    def run_tests(self):
        # Execute code against tests
        loc = {}
        exec(self.code_file, loc)
        try:
            for line in self.test_file.strip().split("\n"):
                exec(line, loc)
            return "SUCCESS: All tests passed!"
        except AssertionError:
            return "FAIL: AssertionError on add_tax(200). Expected 220, got 210!"

    def patch_code(self, new_code):
        self.code_file = new_code
        return "SUCCESS: Code patched."

if __name__ == "__main__":
    env = MockCodingEnvironment()
    print("Initial Test Run Result:\n", env.run_tests())

    # Simulated ReAct Agent Step 1
    thought_1 = "Test failed because add_tax adds flat 10 instead of 10% (0.10 * price)."
    action_1 = "def add_tax(price):\n    return price + price * 0.10"
    print(f"\n[Agent Thought]: {thought_1}")
    print("[Agent Action] : Applying surgical patch...")
    env.patch_code(action_1)

    # Simulated ReAct Agent Step 2: Verification
    obs = env.run_tests()
    print(f"[Observation]  : {obs}")
