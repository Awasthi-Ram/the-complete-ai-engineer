1. The Two Physical Regimes of LLM Inference

Serving Large Language Models is fundamentally distinct from traditional deep learning inference (such as convolutional image classification or speech recognition). Generating autoregressive text spans two completely different physical operating regimes:

Inference Phase Physical Mechanism Hardware Bottleneck Arithmetic Intensity GPU Core Utilization
1. Prefill Phase (Prompt Processing) Ingests the entire prompt sequence ($S$ tokens) and processes all tokens concurrently in a single forward pass. Compute-Bound (FLOPs) High ($I \gg 100 \text{ FLOPs/byte}$) High ($>90\%$ Tensor Core saturation).
2. Decode Phase (Token Generation) Autoregressively generates 1 token at a time. The GPU must stream all 70 Billion weights from HBM to registers to compute just 1 token! Memory-Bandwidth Bound Extremely Low ($I \approx 1 \text{ to } 2 \text{ FLOPs/byte}$) Extremely Low ($<5\%$ ALU utilization). Tensor cores sit idle waiting for memory bus transfers.

2. PagedAttention: Virtual Memory for KV Caches (Kwon et al., 2023)

In standard PyTorch serving (e.g. Hugging Face generate()), memory for a request's KV Cache must be pre-allocated contiguously in GPU VRAM for the maximum possible sequence length (e.g. 4,096 tokens). If the user only generates 150 tokens, over 90% of allocated memory is completely wasted! Traditional serving engines waste between 60% and 80% of total GPU VRAM due to internal and external memory fragmentation.

Figure 5.10.1: Memory management in LLM serving. Traditional contiguous memory allocation wastes 60-80% of VRAM due to internal and external fragmentation. vLLM PagedAttention applies virtual memory paging to KV caches, dynamically allocating non-contiguous physical memory blocks with near-zero waste.

🏆 The vLLM PagedAttention Architecture

Inspired by classical Operating System Virtual Memory Paging, Woosuk Kwon et al. (UC Berkeley) introduced PagedAttention:

  1. The continuous KV Cache is partitioned into fixed-size Physical Blocks (e.g. 16 or 32 tokens per block).
  2. Physical blocks do not need to reside contiguously in physical GPU memory; they can be scattered across arbitrary non-contiguous VRAM memory addresses.
  3. A centralized Block Table maintains the translation from logical token positions to physical block pointers.
  4. New memory blocks are allocated strictly on-demand as new tokens are emitted!

The Quantitative Impact: PagedAttention slashes KV cache memory waste from $70\%$ down to under $4\%$! This freed memory allows the inference server to increase batch sizes by $2\times$ to $4\times$, doubling serving throughput on the exact same GPU hardware.

3. Continuous (Iteration-Level) Batching

Traditional static batching processes a fixed group of requests together. If Request A finishes after 20 tokens while Request B requires 800 tokens, the GPU slots allocated to Request A sit completely idle for 780 cycles waiting for Request B to complete.

Continuous Batching (Iteration-Level Scheduling) operates at the granularity of individual token generation steps:

  • At every single decoding step, the iteration scheduler inspects the batch.
  • Requests that emit an <|end_of_text|> token are immediately evicted from the active batch, freeing their physical blocks.
  • Newly arriving requests in the queue are instantly inserted into the freed batch slots without waiting for a new batch cycle!

4. Speculative Decoding (Leviathan et al., 2022)

Can we make a 70B parameter model generate tokens $2\times$ faster without losing a single drop of mathematical quality? Speculative Decoding pairs a small, fast Draft Model (e.g. 1B parameters) with a large Target Model (70B parameters):

  1. The fast draft model autoregressively guesses $\gamma = 4$ speculative tokens in 4 quick low-cost steps.
  2. The large target model runs a single parallel forward pass across all $\gamma$ candidate tokens simultaneously (which takes the exact same compute time as generating 1 token!).
  3. The target model verifies the candidate tokens using modified rejection sampling. If tokens 1, 2, and 3 are accepted, all 3 tokens are emitted in the time it usually takes to generate 1!

Mathematically, the output distribution is provably identical to the target model alone, achieving a $2\times$ to $3\times$ latency reduction.

Arithmetic Intensity & Roofline Model Analysis on NVIDIA H100 GPU:

An engineer deploys an unquantized 70-Billion parameter foundation model ($N = 70 \times 10^9$) in standard 16-bit precision ($2 \text{ bytes/weight}$) on a single NVIDIA H100 SXM GPU. The H100 specifications are:

  • Peak BF16 Tensor Core Compute: $C_{\text{peak}} = 1,979 \text{ TFLOPs} = 1.979 \times 10^{15} \text{ FLOPs/sec}$.
  • Peak HBM3 Memory Bandwidth: $B_{\text{peak}} = 3.35 \text{ TB/s} = 3.35 \times 10^{12} \text{ bytes/sec}$.
  1. Calculate the Ridge Point (Machine Balance Arithmetic Intensity) $I^* = \frac{C_{\text{peak}}}{B_{\text{peak}}}$ of the H100 GPU.
  2. For the autoregressive Decode phase with batch size $B = 1$:
    • Calculate the bytes transferred from HBM to stream the weights to compute 1 token.
    • Calculate the FLOPs required ($2N \text{ FLOPs}$).
    • Compute the operational Arithmetic Intensity $I_{\text{decode}} = \frac{\text{FLOPs}}{\text{Bytes}}$. State whether execution is memory-bound or compute-bound.
  3. Calculate the maximum theoretical single-stream generation speed (tokens/sec) and GPU Tensor Core utilization percentage.
  4. Calculate the minimum batch size $B_{\text{roofline}}$ required to shift decoding from the memory-bound regime into the compute-bound regime.
✓ Complete Step-by-Step Arithmetic Solution

Step 1: Machine Balance Ridge Point $I^*$:
$$I^* = \frac{C_{\text{peak}}}{B_{\text{peak}}} = \frac{1.979 \times 10^{15} \text{ FLOPs/s}}{3.35 \times 10^{12} \text{ bytes/s}} \approx \mathbf{590.75 \text{ FLOPs/byte}}$$ Any workload with arithmetic intensity $I < 590.75 \text{ FLOPs/byte}$ is strictly memory-bandwidth bound.

Step 2: Decode Phase Arithmetic Intensity ($B = 1$):
Weight data transferred from HBM to registers: $$\text{Memory} = 70 \times 10^9 \text{ params} \times 2 \text{ bytes/param} = 140 \times 10^9 \text{ bytes} = \mathbf{140.0 \text{ GB}}$$ FLOPs to compute 1 token: $$\text{Compute} = 2 \times N = 2 \times 70 \times 10^9 = \mathbf{140 \times 10^9 \text{ FLOPs (140 GFLOPs)}}$$ Arithmetic Intensity: $$I_{\text{decode}} = \frac{140 \times 10^9 \text{ FLOPs}}{140 \times 10^9 \text{ bytes}} = \mathbf{1.000 \text{ FLOP/byte}}$$ Since $1.000 \ll 590.75$, the decode phase is violently memory-bandwidth bound (by a factor of nearly $600\times$!).

Step 3: Maximum Single-Stream Generation Speed:
Time required to stream 140 GB over the $3,350 \text{ GB/s}$ bus: $$T_{\text{token}} = \frac{140.0 \text{ GB}}{3,350 \text{ GB/s}} \approx \mathbf{0.04179 \text{ seconds (41.79 ms/token)}}$$ Maximum single-stream throughput: $$\text{Throughput} = \frac{1}{0.04179 \text{ s}} \approx \mathbf{23.93 \text{ tokens/sec}}$$ Actual compute FLOPs per second achieved: $$\text{Achieved FLOPs} = 23.93 \times 140 \times 10^9 = 3.35 \times 10^{12} \text{ FLOPs/sec} = 3.35 \text{ TFLOPs}$$ Tensor Core Utilization: $$\text{Utilization} = \frac{3.35 \text{ TFLOPs}}{1,979 \text{ TFLOPs}} \times 100\% \approx \mathbf{0.169\%}$$ Over $99.8\%$ of the H100's Tensor Cores sit completely idle waiting for weights to travel over the memory bus!

Step 4: Batch Size to Saturate Compute ($B_{\text{roofline}}$):
When batch size is $B$, weights are transferred once but multiplied against $B$ input tokens: $$I(B) = \frac{2 \times B \times N}{2 \times N} = B \text{ FLOPs/byte}$$ To reach the ridge point $I^* = 590.75$: $$B_{\text{roofline}} \ge \lceil 590.75 \rceil = \mathbf{591 \text{ requests}}$$ To saturate the H100's compute capabilities, an enterprise must batch at least 591 concurrent user requests together!

PagedAttention allocates blocks strictly as tokens arrive, recovering all 245.76 GB and quadrupling serving capacity.

Problem 5.10.3 Tier 2: Applied Engineering Trace Google DeepMind

Speculative Decoding Modified Rejection Sampling Trace:

A fast Draft Model $\mathcal{M}_d$ speculates $\gamma = 3$ candidate tokens: $[x_1, x_2, x_3]$. The Target Model $\mathcal{M}_t$ runs a single parallel forward pass to evaluate the conditional probability distributions.

The probabilities assigned by both models for each candidate token given prior context are:

  • Token $x_1$: $q_1(x_1) = 0.80$ (Draft), $p_1(x_1) = 0.60$ (Target)
  • Token $x_2$: $q_2(x_2) = 0.40$ (Draft), $p_2(x_2) = 0.50$ (Target)
  • Token $x_3$: $q_3(x_3) = 0.70$ (Draft), $p_3(x_3) = 0.70$ (Target)

In Speculative Decoding, candidate token $x_i$ is accepted with probability:

$$\alpha_i = \min\left( 1, \, \frac{p_i(x_i)}{q_i(x_i)} \right)$$

If token $x_i$ is rejected, the loop stops immediately; token $x_i$ is resampled from the modified residual distribution $p'_i(x) \propto \max(0, p_i(x) - q_i(x))$, and subsequent speculative tokens are discarded.

Uniform random numbers drawn during verification: $u_1 = 0.70, u_2 = 0.25, u_3 = 0.85$.

  1. Calculate the acceptance probability $\alpha_1, \alpha_2, \alpha_3$ for all three tokens.
  2. Compare the random draws $u_i$ against $\alpha_i$ to determine which tokens are accepted.
  3. Identify the first rejected token and state what action the engine takes.
  4. Calculate the total number of verified tokens emitted in this single target forward pass.
✓ Complete Step-by-Step Algorithmic Trace

Step 1: Compute Acceptance Probabilities:

  • Token 1: $$\alpha_1 = \min\left(1, \frac{p_1}{q_1}\right) = \min\left(1, \frac{0.60}{0.80}\right) = \min(1, 0.75) = \mathbf{0.7500 \text{ (75.0\%)}}$$
  • Token 2: $$\alpha_2 = \min\left(1, \frac{p_2}{q_2}\right) = \min\left(1, \frac{0.50}{0.40}\right) = \min(1, 1.25) = \mathbf{1.0000 \text{ (100.0\%)}}$$
  • Token 3: $$\alpha_3 = \min\left(1, \frac{p_3}{q_3}\right) = \min\left(1, \frac{0.70}{0.70}\right) = \mathbf{1.0000 \text{ (100.0\%)}}$$

Step 2 & 3: Sequential Verification Trace:

  • Testing Token 1: Random draw $u_1 = 0.70$. Condition: $u_1 \le \alpha_1 \iff 0.70 \le 0.75$. Result: ACCEPTED! Token $x_1$ is committed.
  • Testing Token 2: Random draw $u_2 = 0.25$. Condition: $u_2 \le \alpha_2 \iff 0.25 \le 1.00$. Result: ACCEPTED! Token $x_2$ is committed.
  • Testing Token 3: Random draw $u_3 = 0.85$. Condition: $u_3 \le \alpha_3 \iff 0.85 \le 1.00$. Result: ACCEPTED! Token $x_3$ is committed.

Step 4: Final Emission Count:
All $\gamma = 3$ speculative tokens were accepted! In addition, the target model's forward pass computed the next-token probability distribution following token $x_3$, from which it samples 1 bonus token $x_4 \sim p_4$. Total tokens emitted in this single forward pass: $$\text{Total Emitted} = \gamma + 1 = 3 + 1 = \mathbf{4 \text{ tokens!}}$$ The target model generated 4 tokens in the time it normally takes to generate 1 token, achieving an instantaneous $4\times$ speedup!

Problem 5.10.4 Tier 2: Applied Engineering Trace UC Berkeley Anyscale

vLLM Paged Block Allocator & Copy-on-Write (CoW) Branching Trace:

In parallel sampling (e.g. beam search or generating $N = 2$ completions for a single prompt), vLLM optimizes memory using Copy-on-Write (CoW).

Block size $B = 16$ tokens. Free physical block pool: $[10, 11, 12, 13, 14, 15]$.

Execution sequence:

  1. User submits a prompt of $S = 28$ tokens. Request 1 allocates initial physical blocks. Trace the allocated physical block IDs and their reference counts.
  2. The user requests $N = 2$ completions (Branch A and Branch B) sharing the prompt. Trace the block tables for Branch A and Branch B, and update block reference counts.
  3. Both branches generate tokens:
    • Token 29 is generated by Branch A and Branch B (both appending to the shared block). Trace how CoW handles appending to a shared block.
✓ Complete Step-by-Step Block Manager Trace

Step 1: Initial Prompt Allocation ($S = 28$ tokens):
Number of blocks required: $\lceil 28 / 16 \rceil = 2 \text{ blocks}$. Blocks allocated from pool: Block 10 (tokens 1–16) and Block 11 (tokens 17–28, with 4 free slots). Block Table: $$\text{Prompt}: \quad [\text{Block 10, Block 11}]$$ Reference Counts: $\text{ref\_count}[10] = 1, \quad \text{ref\_count}[11] = 1$. Free pool remaining: $[12, 13, 14, 15]$.

Step 2: Forking Parallel Sampling Branches (Branch A & Branch B):
Rather than copying all 28 tokens ($320 \text{ KB} \times 28 \approx 9 \text{ MB}$ of VRAM), vLLM simply creates two logical block tables pointing to the exact same physical blocks: $$\text{Branch A}: \quad [\text{Block 10, Block 11}]$$ $$\text{Branch B}: \quad [\text{Block 10, Block 11}]$$ Increment reference counts: $$\text{ref\_count}[10] = 2, \quad \text{ref\_count}[11] = 2$$ Memory consumed to fork the branch: 0 bytes of GPU memory (only two pointer copies in CPU RAM)!

Step 3: Appending Token 29 via Copy-on-Write (CoW):
Now Branch A generates token $t_{29}^A$, and Branch B generates a different token $t_{29}^B$. Both branches need to write to position 29 in Block 11. Since $\text{ref\_count}[11] = 2 > 1$, writing directly would corrupt Branch B's history! vLLM detects the multi-reference status and triggers Copy-on-Write:

  1. Branch A retains Block 11 (reference count decrements: $\text{ref\_count}[11] = 1$). Token $t_{29}^A$ is written to slot 13 of Block 11.
  2. For Branch B, vLLM pops a clean block from the free pool: Block 12.
  3. It copies the first 12 prompt tokens from Block 11 into Block 12, writes token $t_{29}^B$ to slot 13, and sets $\text{ref\_count}[12] = 1$.
Updated Block Tables: $$\text{Branch A}: \quad [\text{Block 10, Block 11}]$$ $$\text{Branch B}: \quad [\text{Block 10, Block 12}]$$ Free pool remaining: $[13, 14, 15]$. Notice that Block 10 remains permanently shared ($\text{ref\_count}[10] = 2$), completely eliminating duplicate storage for the shared prompt!

Problem 5.10.5 Tier 3: FAANG / Research Lab Proof Google Research DeepMind

Mathematical Proof: Distribution Invariance of Speculative Decoding via Modified Rejection Sampling:

In Speculative Decoding (Leviathan et al., 2022), a candidate token $x \sim q(x)$ is sampled from draft distribution $q$. The target model evaluates target distribution $p(x)$. Candidate $x$ is accepted with probability:

$$\alpha(x) = \min\left(1, \, \frac{p(x)}{q(x)}\right)$$

If $x$ is rejected, a new token $x'$ is sampled from the residual distribution:

$$p'(x) = \frac{\max(0, \, p(x) - q(x))}{\sum_{y} \max(0, \, p(y) - q(y))}$$
  1. Prove that the total probability of acceptance is $\beta = \sum_x q(x) \alpha(x) = 1 - \frac{1}{2} \|p - q\|_1$.
  2. Prove that the normalizing denominator of the residual distribution satisfies: $$\sum_y \max(0, p(y) - q(y)) = 1 - \beta$$
  3. Prove that the final marginal distribution of the emitted token $X_{\text{final}}$ is identically equal to the target distribution $p(x)$: $$\mathbb{P}(X_{\text{final}} = x) = p(x) \quad \forall x$$
✓ Complete Mathematical Invariance Proof

Part 1: Acceptance Probability $\beta$:
Using the identity $\min(a, b) = a - \max(0, a - b)$: $$\alpha(x) = \min\left(1, \frac{p(x)}{q(x)}\right) \implies q(x) \alpha(x) = \min(q(x), p(x))$$ The overall acceptance probability is: $$\beta = \sum_x q(x) \alpha(x) = \sum_x \min(q(x), p(x))$$ Using the mathematical identity $\min(a, b) = \frac{a + b - |a - b|}{2}$: $$\beta = \sum_x \frac{q(x) + p(x) - |p(x) - q(x)|}{2} = \frac{1}{2}\sum_x q(x) + \frac{1}{2}\sum_x p(x) - \frac{1}{2}\sum_x |p(x) - q(x)|$$ Since $\sum q(x) = 1$ and $\sum p(x) = 1$: $$\mathbf{\beta = 1 - \frac{1}{2} \|p - q\|_1} \quad \blacksquare$$ The acceptance probability equals 1 minus the total variation distance between draft and target!

Part 2: Residual Normalization Constant:
Using $\max(0, a - b) = a - \min(a, b)$: $$\sum_y \max(0, p(y) - q(y)) = \sum_y [p(y) - \min(p(y), q(y))] = \sum_y p(y) - \sum_y \min(p(y), q(y)) = 1 - \beta \quad \blacksquare$$ Thus the residual distribution is: $$p'(x) = \frac{\max(0, p(x) - q(x))}{1 - \beta}$$

Part 3: Marginal Distribution Equivalence Proof:
An emitted token $X_{\text{final}}$ can be produced via two mutually exclusive events:

  1. The candidate $x \sim q$ is sampled and accepted (probability $q(x) \alpha(x)$).
  2. A candidate is rejected (probability $1 - \beta$), and $x$ is drawn from the residual distribution $p'(x)$ (probability $(1 - \beta) p'(x)$).
Total probability of emitting token $x$: $$\mathbb{P}(X_{\text{final}} = x) = q(x) \alpha(x) + (1 - \beta) p'(x)$$ Substitute $q(x) \alpha(x) = \min(q(x), p(x))$ and $(1 - \beta) p'(x) = \max(0, p(x) - q(x))$: $$\mathbb{P}(X_{\text{final}} = x) = \min(q(x), p(x)) + \max(0, p(x) - q(x))$$ Using the algebraic identity $\min(a, b) + \max(0, a - b) = a$ (for $a = p(x)$ and $b = q(x)$): If $p(x) \le q(x)$: $\min(p(x), q(x)) + 0 = p(x)$.
If $p(x) > q(x)$: $q(x) + (p(x) - q(x)) = p(x)$.
In all cases: $$\mathbf{\mathbb{P}(X_{\text{final}} = x) = p(x)} \quad \blacksquare$$ The output distribution is provably, unconditionally identical to the target model! Speculative decoding is lossless: zero degradation in reasoning, perplexity, or MMLU scores.

Problem 5.10.6 Tier 3: FAANG / Research Lab Proof OpenAI DeepMind

Mathematical Proof: Expected Speedup Factor and Optimal Speculative Lookahead:

In Speculative Decoding with lookahead $\gamma$, let the per-token acceptance rate be independent and identically distributed with constant probability $\alpha \in (0, 1)$. Let $c = \frac{T_{\text{draft}}}{T_{\text{target}}}$ be the cost ratio of running one draft step relative to one target model forward pass ($c \ll 1$, typically $0.05$).

  1. Prove that the expected number of accepted tokens $\mathbb{E}[M]$ per verification round is: $$\mathbb{E}[M] = \frac{1 - \alpha^{\gamma+1}}{1 - \alpha}$$
  2. Formulate the total execution time of one speculative round as $T_{\text{round}} = (\gamma c + 1) T_{\text{target}}$. Derive the theoretical speedup factor: $$S(\gamma) = \frac{\mathbb{E}[M]}{\gamma c + 1} = \frac{1 - \alpha^{\gamma+1}}{(1 - \alpha)(\gamma c + 1)}$$
  3. For $\alpha = 0.80$ and $c = 0.05$, compute $S(\gamma)$ for $\gamma = 1, 2, 3, 4, 5$, and identify the optimal draft length $\gamma^*$.
✓ Complete Mathematical Derivation & Optimization

Part 1: Derivation of Expected Tokens $\mathbb{E}[M]$:
Let $K \in \{0, 1, \dots, \gamma\}$ be the number of consecutive accepted draft tokens. Since $K \ge k$ requires all first $k$ tokens to be accepted: $$\mathbb{P}(K \ge k) = \alpha^k \quad \text{for } k = 1, 2, \dots, \gamma$$ Because the target model always emits 1 bonus/resampled token regardless of whether $K = 0$ or $K = \gamma$, the total tokens emitted is $M = K + 1$. Using the identity for expectation of non-negative integer random variables $\mathbb{E}[K] = \sum_{k=1}^\gamma \mathbb{P}(K \ge k)$: $$\mathbb{E}[K] = \sum_{k=1}^\gamma \alpha^k = \alpha \frac{1 - \alpha^\gamma}{1 - \alpha}$$ Total expected tokens: $$\mathbb{E}[M] = \mathbb{E}[K] + 1 = 1 + \alpha \frac{1 - \alpha^\gamma}{1 - \alpha} = \frac{1 - \alpha + \alpha - \alpha^{\gamma+1}}{1 - \alpha} = \mathbf{\frac{1 - \alpha^{\gamma+1}}{1 - \alpha}} \quad \blacksquare$$

Part 2: Speedup Factor Derivation:
Without speculative decoding, generating $\mathbb{E}[M]$ tokens takes $\mathbb{E}[M] \cdot T_{\text{target}}$ time. With speculative decoding, running $\gamma$ draft steps costs $\gamma T_{\text{draft}} = \gamma c T_{\text{target}}$. Verifying them in the target model takes $1 \cdot T_{\text{target}}$. Total round time: $$T_{\text{round}} = (\gamma c + 1) T_{\text{target}}$$ The speedup factor is: $$\mathbf{S(\gamma) = \frac{\mathbb{E}[M] T_{\text{target}}}{T_{\text{round}}} = \frac{1 - \alpha^{\gamma+1}}{(1 - \alpha)(\gamma c + 1)}} \quad \blacksquare$$

Part 3: Numerical Optimization ($\alpha = 0.80, c = 0.05$):
Here $1 - \alpha = 0.20$.

  • $\gamma = 1$: $\mathbb{E}[M] = \frac{1 - 0.80^2}{0.20} = \frac{0.36}{0.20} = 1.80$. Cost: $1(0.05) + 1 = 1.05$. $$S(1) = \frac{1.80}{1.05} \approx \mathbf{1.714\times}$$
  • $\gamma = 2$: $\mathbb{E}[M] = \frac{1 - 0.80^3}{0.20} = \frac{0.488}{0.20} = 2.44$. Cost: $2(0.05) + 1 = 1.10$. $$S(2) = \frac{2.44}{1.10} \approx \mathbf{2.218\times}$$
  • $\gamma = 3$: $\mathbb{E}[M] = \frac{1 - 0.80^4}{0.20} = \frac{0.5904}{0.20} = 2.952$. Cost: $3(0.05) + 1 = 1.15$. $$S(3) = \frac{2.952}{1.15} \approx \mathbf{2.567\times}$$
  • $\gamma = 4$: $\mathbb{E}[M] = \frac{1 - 0.80^5}{0.20} = \frac{0.67232}{0.20} = 3.3616$. Cost: $4(0.05) + 1 = 1.20$. $$S(4) = \frac{3.3616}{1.20} \approx \mathbf{2.801\times} \quad \text{★ OPTIMAL}$$
  • $\gamma = 5$: $\mathbb{E}[M] = \frac{1 - 0.80^6}{0.20} = \frac{0.73786}{0.20} = 3.6893$. Cost: $5(0.05) + 1 = 1.25$. $$S(5) = \frac{3.6893}{1.25} \approx \mathbf{2.951\times}$$
  • $\gamma = 6$: $\mathbb{E}[M] = \frac{1 - 0.80^7}{0.20} = \frac{0.79028}{0.20} = 3.9514$. Cost: $6(0.05) + 1 = 1.30$. $$S(6) = \frac{3.9514}{1.30} \approx \mathbf{3.039\times}$$
Beyond $\gamma = 4 \text{ to } 5$, diminishing returns set in: $\alpha^k$ drops and draft cost accumulates. In production, setting $\mathbf{\gamma = 4 \text{ or } 5}$ achieves the optimal peak $2.8\times$ to $3.0\times$ speedup.

Problem 5.10.7 Tier 4: Conceptual Trap MCQ NVIDIA Google

Conceptual Trap: The "Decode Starvation / Preemption Bubble" in Mixed Workloads:

A production vLLM instance concurrently serves 100 streaming conversational users (Decode phase). A new request arrives containing an extremely long prompt of $S = 8,192$ tokens.

The server pauses decoding to process the 8,192-token prefill in a single forward pass, taking 450 ms. During this window, all 100 streaming users experience an abrupt 450 ms jitter pause in their token stream, violating their 50ms P99 latency SLA.

Which of the following describes the production systems architecture introduced in Sarathi and vLLM to solve this decode starvation?

  • (A) Drop all prompts longer than 1,024 tokens.
  • (B) Chunked Prefill: Slicing long prefill prompts into smaller chunks (e.g. 512 tokens per step) and co-scheduling them in the same iteration batch alongside decode requests. This caps the iteration time at ~25ms while steadily advancing both prefill and decode phases simultaneously.
  • (C) Switch from FP16 to INT4 quantization, which eliminates the prefill phase completely.
  • (D) Run the prefill on CPU RAM using NumPy.
✓ Complete Distractor Analysis & Architectural Rationale

Correct Answer: (B)

Exhaustive Distractor Analysis:

  • Why (B) is Correct: In naive serving engines, a large prefill ($O(S^2)$ attention computation) monopolizes the GPU's Tensor Cores for hundreds of milliseconds, starving existing decoding tokens and causing severe tail-latency spikes. Chunked Prefill (Agrawal et al., 2023) solves this by chunking long prompts: an 8,192-token prompt is processed across 16 consecutive steps of 512 tokens each. In each step, the 512 prefill tokens are batched together with the 100 decoding tokens. Because decode uses memory bandwidth and prefill uses compute, they complement each other's hardware utilization, achieving near-perfect compute-bandwidth saturation while keeping token generation P99 latency under 30 ms!
  • Why (A) is Incorrect: Enterprise use cases (RAG, document analysis) routinely require 8k to 32k contexts; dropping them breaks customer contracts.
  • Why (C) is Incorrect: Quantization reduces memory footprint, but prefill computation is still quadratic in sequence length and cannot be eliminated.
  • Why (D) is Incorrect: Running 8k prefill on CPU takes 10+ seconds, drastically worsening latency.

Problem 5.10.8 Tier 4: Conceptual Trap MCQ Meta Amazon Web Services

Conceptual Trap: Tensor Parallelism Communication Overhead across PCIe vs. NVLink:

An engineer deploys a 70B parameter model across an 8-GPU node using Megatron-style Tensor Parallelism (TP = 8). In each Transformer layer, TP requires two All-Reduce collective communication operations (one after Attention, one after MLP):

$$\text{All-Reduce Communication per Layer} = 2 \times \frac{2(TP - 1)}{TP} \times B \times S \times d$$

When tested on an NVIDIA HGX H100 server equipped with NVLink (900 GB/s bidirectional bandwidth), serving achieves 4,200 tokens/sec. When deployed on a low-cost commodity server with 8 GPUs connected over PCIe Gen 4 (32 GB/s bandwidth), throughput collapses to under 180 tokens/sec ($23\times$ slowdown!).

Which of the following explains this collapse and dictates the correct distributed topology?

  • (A) Tensor Parallelism communicates activations at every single layer ($2 \times 80 = 160$ All-Reduces per token). On PCIe, the communication latency ($>50 \mu\text{s}$ per transfer) vastly exceeds the GPU kernel computation time ($<2 \mu\text{s}$), leaving the GPUs stalled waiting on the PCIe bus. On PCIe clusters, engineers must use Pipeline Parallelism (PP) or single-GPU quantization (AWQ/FP8) instead of Tensor Parallelism.
  • (B) PCIe does not support floating point arithmetic.
  • (C) vLLM automatically disables PagedAttention when more than 4 GPUs are detected.
  • (D) All-Reduce requires an odd number of GPUs to avoid deadlock.
✓ Complete Distractor Analysis & Architectural Rationale

Correct Answer: (A)

Exhaustive Distractor Analysis:

  • Why (A) is Correct: Tensor Parallelism splits individual weight matrices column-wise and row-wise within every single layer. For an 80-layer model, calculating 1 token requires $2 \times 80 = 160$ sequential All-Reduce synchronizations! On NVLink ($900 \text{ GB/s}$ with hardware NVSwitch), an All-Reduce completes in sub-microsecond time ($<1 \mu\text{s}$). On PCIe Gen 4 ($32 \text{ GB/s}$ through host CPU root complex), an All-Reduce incurs $30 \text{ to } 60 \mu\text{s}$ of latency. Multiplying by 160 transfers adds $5 \text{ to } 10 \text{ ms}$ of pure idle bus latency per token! Therefore, Tensor Parallelism is strictly restricted to NVLink intra-node topologies. On PCIe nodes, engineers must deploy Pipeline Parallelism (PP) (which communicates only once per pipeline stage boundary) or quantize the model (FP8/AWQ) to run on fewer GPUs without cross-card All-Reduce.
  • Why (B) is Incorrect: PCIe is an interconnection bus protocol; arithmetic is executed by GPU ALUs, not by the bus.
  • Why (C) is Incorrect: vLLM natively supports PagedAttention across arbitrary GPU cluster sizes (TP = 8, 16, 32).
  • Why (D) is Incorrect: All-Reduce runs optimally on powers of 2 (2, 4, 8) using ring or tree algorithms; odd GPU counts actually degrade communication efficiency.

from typing import List, Dict, Optional

class PagedBlockManager:
    def __init__(self, block_size: int = 16, num_gpu_blocks: int = 100):
        self.block_size = block_size
        self.num_gpu_blocks = num_gpu_blocks
        self.free_blocks = list(range(num_gpu_blocks))
        # Maps request_id -> list of allocated physical block IDs
        self.block_tables: Dict[str, List[int]] = {}
        # Physical block ID -> reference count (for Copy-on-Write)
        self.ref_counts = [0] * num_gpu_blocks

    def allocate(self, request_id: str, num_tokens: int) -> List[int]:
        num_blocks_needed = (num_tokens + self.block_size - 1) // self.block_size
        if len(self.free_blocks) < num_blocks_needed:
            raise MemoryError(f"GPU OOM: Needed {num_blocks_needed} blocks, only {len(self.free_blocks)} free.")

        allocated = [self.free_blocks.pop(0) for _ in range(num_blocks_needed)]
        for b in allocated:
            self.ref_counts[b] = 1
        self.block_tables[request_id] = allocated
        return allocated

    def append_token(self, request_id: str, current_token_count: int) -> Optional[int]:
        """Appends 1 token to request. Allocates new block if current block is full."""
        if current_token_count % self.block_size == 0:
            if not self.free_blocks:
                raise MemoryError("GPU VRAM Out of Memory during decoding!")
            new_block = self.free_blocks.pop(0)
            self.ref_counts[new_block] = 1
            self.block_tables[request_id].append(new_block)
            return new_block
        return None

    def free(self, request_id: str):
        blocks = self.block_tables.pop(request_id, [])
        for b in blocks:
            self.ref_counts[b] -= 1
            if self.ref_counts[b] == 0:
                self.free_blocks.append(b)

if __name__ == "__main__":
    manager = PagedBlockManager(block_size=16, num_gpu_blocks=20)
    print(f"Initial Free GPU Physical Blocks: {len(manager.free_blocks)}")

    # Request 1 arrives with 35 prompt tokens (requires 3 blocks: 16 + 16 + 3)
    b1 = manager.allocate("req_1", num_tokens=35)
    print(f"[Req 1 Allocated] Blocks: {b1} (Remaining Free: {len(manager.free_blocks)})")
    assert len(b1) == 3

    # Decode 13 more tokens (total 48 tokens, fills block 3 completely)
    for t in range(36, 49):
        manager.append_token("req_1", t - 1)

    # Decode token 49 (requires 4th block)
    new_b = manager.append_token("req_1", 48)
    print(f"[Req 1 Decode Expansion] Token 49 triggered allocation of Block: {new_b}")
    assert len(manager.block_tables["req_1"]) == 4

    # Evict request upon completion
    manager.free("req_1")
    print(f"[Req 1 Finished] Free Blocks Restored: {len(manager.free_blocks)}")
    assert len(manager.free_blocks) == 20
    print("[SUCCESS] PagedAttention Block Manager Verified.")
