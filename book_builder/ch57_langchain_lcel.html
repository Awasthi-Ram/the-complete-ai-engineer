Foundation • Core Pillar

1. From Brittle Chains to Declarative LCEL

Early iterations of AI orchestration frameworks relied on deeply nested object-oriented class hierarchies (e.g. LLMChain, SequentialChain, TransformChain). These legacy abstractions were notorious for hidden internal mutable state, painful debugging cycles, thread-safety bugs, and an inability to stream tokens natively across asynchronous microservices.

In response, Harrison Chase et al. re-architected LangChain around the LangChain Expression Language (LCEL): a clean, declarative Unix-style piping protocol built entirely on the unified Runnable Interface:

$$\text{Pipeline} = \text{Prompt} \mid \text{Model} \mid \text{OutputParser}$$

Every component in an LCEL pipeline implements a standardized, async-first contract:

  • invoke() / ainvoke(): Synchronous and asynchronous execution on a single input payload.
  • stream() / astream(): Emitting output tokens the microsecond they are generated by the server.
  • batch() / abatch(): Automatic parallelized batch execution across thread pools with dynamic concurrency limits.
  • astream_events(): Emitting fine-grained internal events (model starts, tool calls, token deltas, parser completions) for real-time WebSockets and streaming UI interfaces.

2. The Core LCEL Primitives

1. RunnableParallel (Concurrent Branch Execution)

In production RAG, an incoming user question must simultaneously be embedded for vector retrieval, converted into an SQL keyword query, and passed forward into the prompt context. RunnableParallel executes these branches concurrently across worker threads:

from langchain_core.runnables import RunnableParallel, RunnablePassthrough
from operator import itemgetter

retrieval_chain = RunnableParallel({
    "context": itemgetter("question") | vector_retriever,
    "question": itemgetter("question")
})

2. RunnablePassthrough

Passes inputs through unchanged, allowing intermediate dictionaries to retain original user questions while attaching enriched retrieval context.

3. RunnableLambda

Wraps any standard Python function into an official Runnable, allowing custom business logic (e.g. scrubbing PII, calculating tax, formatting currency) to be inserted directly into the pipeline with full streaming and async support.

3. Deterministic Structured Outputs with Pydantic & Function Calling

In enterprise software, an LLM must never output freeform markdown strings if downstream microservices expect to consume the data. If an agent emits "Sure! Here is the order: ID: 1042, Amount: $49.99", parsing this with regular expressions is an invitation to production outages.

Modern LLMs expose native JSON Schema Function Calling. In LangChain, we bind a strict Pydantic Model using .with_structured_output():

from pydantic import BaseModel, Field

class FinancialExtraction(BaseModel):
    ticker: str = Field(description="Stock ticker symbol")
    revenue_usd: float = Field(description="Total quarterly revenue in USD")
    yoy_growth_percent: float = Field(description="Year-over-year growth percentage")

structured_llm = llm.with_structured_output(FinancialExtraction)

The output is guaranteed to be a typed, validated Pydantic object: result.revenue_usd is a verified float, eliminating JSON parsing crashes entirely!

4. Conversational Memory & State Management in LCEL

In stateless REST APIs, each request is isolated. Conversational agents, however, require multi-turn conversational context. In modern LCEL, memory is handled via RunnableWithMessageHistory coupled with persistent stores (Redis, Postgres, DynamoDB):

Memory Strategy Mechanism Pros Cons / Trade-offs
Buffer Memory Appends raw conversation history verbatim to context Zero loss of detail, simple implementation Context window overflow, exploding token latency & cost
Sliding Window Memory Retains only the last $K$ turns (e.g. $K=10$ messages) Strict upper bound on token consumption Completely forgets instructions given early in conversation
Summary Memory Background LLM summarizes past turns into a concise running profile Retains key facts indefinitely in minimal tokens Additional LLM call per turn adds latency and cost

5. Tool & Function Calling with the @tool Decorator

Modern LLMs are not just passive text predictors; they are active agents equipped with tools to interact with external APIs, databases, and compute environments. LangChain provides the @tool decorator, which automatically derives JSON schemas and type hints from Python function signatures and docstrings:

from langchain_core.tools import tool

@tool
def calculate_compound_interest(principal: float, annual_rate: float, years: int) -> float:
    """
    Calculates compound interest for an investment portfolio.

    Args:
        principal: Initial investment amount in USD.
        annual_rate: Annual interest rate as a decimal (e.g. 0.07 for 7%).
        years: Investment duration in years.
    """
    return round(principal * ((1.0 + annual_rate) ** years), 2)

tools = [calculate_compound_interest]
model_with_tools = llm.bind_tools(tools)

Amdahl's Law & Concurrency Latency in RunnableParallel:

A multi-source enterprise RAG pipeline consists of three sequential pipeline stages:

  1. Stage 1: Query Preprocessing (Sequential): Execution time $T_{\text{pre}} = 40 \text{ ms}$.
  2. Stage 2: Multi-Source Retrieval: Queries three external backends:
    • Vector Database retrieval: $T_{\text{vector}} = 180 \text{ ms}$.
    • SQL Relational Database query: $T_{\text{sql}} = 120 \text{ ms}$.
    • Live Web Search API: $T_{\text{web}} = 260 \text{ ms}$.
  3. Stage 3: LLM Context Synthesis (Sequential): Execution time $T_{\text{llm}} = 520 \text{ ms}$.
  1. Calculate the total pipeline latency $T_{\text{seq}}$ if Stage 2 is executed sequentially.
  2. Calculate the total pipeline latency $T_{\text{parallel}}$ if Stage 2 is orchestrated using RunnableParallel across concurrent worker threads (assume zero thread scheduling overhead).
  3. Compute the speedup factor $S = \frac{T_{\text{seq}}}{T_{\text{parallel}}}$ and the parallel latency savings percentage.
✓ Complete Step-by-Step Arithmetic Solution

Step 1: Sequential Latency $T_{\text{seq}}$:
Under sequential execution, Stage 2 latency is the direct sum of all three queries: $$T_{\text{stage2, seq}} = 180 + 120 + 260 = 560 \text{ ms}$$ Total pipeline sequential latency: $$T_{\text{seq}} = T_{\text{pre}} + T_{\text{stage2, seq}} + T_{\text{llm}} = 40 + 560 + 520 = \mathbf{1,120 \text{ ms (1.12 seconds)}}$$

Step 2: Concurrent Latency $T_{\text{parallel}}$ with RunnableParallel:
When executed concurrently in parallel threads, the latency of Stage 2 is bounded by the slowest branch (critical path): $$T_{\text{stage2, parallel}} = \max(T_{\text{vector}}, T_{\text{sql}}, T_{\text{web}}) = \max(180, 120, 260) = 260 \text{ ms}$$ Total pipeline concurrent latency: $$T_{\text{parallel}} = T_{\text{pre}} + T_{\text{stage2, parallel}} + T_{\text{llm}} = 40 + 260 + 520 = \mathbf{820 \text{ ms (0.82 seconds)}}$$

Step 3: Speedup and Savings Percentage:
$$\text{Speedup Factor } S = \frac{T_{\text{seq}}}{T_{\text{parallel}}} = \frac{1,120}{820} \approx \mathbf{1.366 \times \text{ Speedup}}$$ Latency savings: $$\Delta T = 1,120 - 820 = 300 \text{ ms saved}$$ $$\text{Percentage Reduction} = \frac{300}{1,120} \times 100\% \approx \mathbf{26.79\%}$$ By wrapping the three retrieval calls in `RunnableParallel`, overall end-to-end user latency drops by more than a quarter-second with zero algorithmic changes!

Problem 5.7.2 Tier 1: Direct Formula Drill Google Microsoft

Truncated Exponential Backoff with Full Jitter Sizing Arithmetic:

In production LCEL, API calls to frontier LLMs encounter HTTP 429 rate limits. LangChain's .with_retry() implements Truncated Exponential Backoff with Full Jitter (AWS Architecture standard):

$$t_{\text{wait}}(k) \sim \mathcal{U}\left( 0, \, \min(t_{\max}, \, t_{\text{base}} \times 2^k) \right)$$

where $k$ is the zero-indexed retry attempt ($k = 0, 1, 2, 3$), base sleep time $t_{\text{base}} = 1.0 \text{ s}$, and maximum cap $t_{\max} = 10.0 \text{ s}$.

  1. Calculate the deterministic upper bound $B_k = \min(t_{\max}, t_{\text{base}} \times 2^k)$ for retry attempts $k = 0, 1, 2, 3, 4$.
  2. Calculate the expected wait time $\mathbb{E}[t_{\text{wait}}(k)]$ for each of the first 4 attempts ($k = 0, 1, 2, 3$).
  3. If an upstream service suffers a hard 7-second outage, calculate the expected cumulative time elapsed before a client makes its 4th attempt (after 3 failures: $k = 0, 1, 2$).
✓ Complete Step-by-Step Arithmetic Solution

Step 1: Upper Bound $B_k$ Calculation:
Given $t_{\text{base}} = 1.0 \text{ s}$ and $t_{\max} = 10.0 \text{ s}$:

  • Attempt $0$ ($k=0$): $B_0 = \min(10.0, 1.0 \times 2^0) = \min(10.0, 1.0) = \mathbf{1.0 \text{ s}}$
  • Attempt $1$ ($k=1$): $B_1 = \min(10.0, 1.0 \times 2^1) = \min(10.0, 2.0) = \mathbf{2.0 \text{ s}}$
  • Attempt $2$ ($k=2$): $B_2 = \min(10.0, 1.0 \times 2^2) = \min(10.0, 4.0) = \mathbf{4.0 \text{ s}}$
  • Attempt $3$ ($k=3$): $B_3 = \min(10.0, 1.0 \times 2^3) = \min(10.0, 8.0) = \mathbf{8.0 \text{ s}}$
  • Attempt $4$ ($k=4$): $B_4 = \min(10.0, 1.0 \times 2^4) = \min(10.0, 16.0) = \mathbf{10.0 \text{ s}}$ (Capped!)

Step 2: Expected Wait Time $\mathbb{E}[t_{\text{wait}}(k)]$:
Since wait time is drawn from a uniform distribution $\mathcal{U}(0, B_k)$, the expected value is $\frac{B_k}{2}$:

  • $\mathbb{E}[t_{\text{wait}}(0)] = \frac{1.0}{2} = \mathbf{0.50 \text{ s}}$
  • $\mathbb{E}[t_{\text{wait}}(1)] = \frac{2.0}{2} = \mathbf{1.00 \text{ s}}$
  • $\mathbb{E}[t_{\text{wait}}(2)] = \frac{4.0}{2} = \mathbf{2.00 \text{ s}}$
  • $\mathbb{E}[t_{\text{wait}}(3)] = \frac{8.0}{2} = \mathbf{4.00 \text{ s}}$

Step 3: Cumulative Elapsed Wait Time:
Before making attempt 4, the client sleeps across attempts $k = 0, 1, 2$: $$\mathbb{E}[\text{Total Elapsed Sleep}] = \mathbb{E}[t_0] + \mathbb{E}[t_1] + \mathbb{E}[t_2] = 0.50 + 1.00 + 2.00 = \mathbf{3.50 \text{ s}}$$ Adding the execution timeouts of the failed queries (e.g. 1s per timeout), the 4th attempt occurs at approximately $3.5 + 3.0 = 6.5\text{s}$, smoothly bridging the outage without overwhelming the server with synchronous retry storms.

Step 3: Perceived Latency Comparison:

Problem 5.7.4 Tier 2: Applied Engineering Trace OpenAI Microsoft

Grammar-Constrained JSON Schema Decoding State Machine Trace:

When LangChain invokes model.with_structured_output(Schema), production backends enforce a Context-Free Grammar (CFG) logit mask at the token generation layer. Consider the target Pydantic schema:

class ApprovalStatus(BaseModel):
    decision: Literal["APPROVED", "REJECTED"]
    code: int # must be 1 to 999

At decoding step $t$, the LLM vocabulary has size $|\mathcal{V}| = 32,000$. Trace the grammar state machine and logit masking behavior:

  1. At step $t = 1$, the grammar requires opening the JSON object: {"decision": ". How does the logit mask restrict the active vocabulary?
  2. Once {"decision": " is emitted, calculate the exact number of valid next tokens if "APPROVED" and "REJECTED" are individual tokens in $\mathcal{V}$. What value is assigned to all other 31,998 token logits?
  3. Explain why grammar-constrained decoding guarantees that Pydantic validation error rate is identically zero ($0.0\%$).
✓ Complete Step-by-Step State Machine Trace

Step 1: Step $t=1$ Deterministic Masking:
The CFG parser knows the exact JSON schema. The first token must begin with {. All tokens in $\mathcal{V}$ that do not begin with whitespace or { are masked by setting their unnormalized logits to $-\infty$: $$\text{Logit}_i = -\infty \quad \forall i \notin \text{AllowedTokens}(\text{State}_0)$$ Consequently, $\text{Softmax}(\text{Logits})$ assigns $100\%$ probability mass strictly to valid JSON prefix tokens.

Step 2: Restricted Literal State Masking:
Once the key "decision": " has been decoded, the CFG state transitions to the Literal["APPROVED", "REJECTED"] enumeration state: $$\text{Valid Set} = \{\text{Token("APPROVED")}, \text{Token("REJECTED")}\}$$ Number of valid tokens = exactly 2 tokens! For all other 31,998 tokens in the vocabulary: $$\text{Logit}_j = -\infty \quad \implies \quad P(\text{Token}_j) = \frac{e^{-\infty}}{e^{\text{logit}_{\text{APP}}} + e^{\text{logit}_{\text{REJ}}}} = \mathbf{0.0}$$ The model is physically prevented from outputting any other string (such as "MAYBE", "PENDING", or markdown commentary)!

Step 3: Zero-Defect Pydantic Guarantee:
In traditional prompting without CFG masking, an LLM might generate {"decision": "Approved"} (wrong case) or {"decision": "None"}, which causes Pydantic to throw a fatal ValidationError. Under grammar-constrained logit masking, the generator cannot sample any token sequence that violates the schema, guaranteeing that every single output passes Pydantic validation with 100% mathematical certainty.

Problem 5.7.5 Tier 3: FAANG / Research Lab Proof Google Research Meta

Mathematical Proof: Category-Theoretic Monadic Formulation of LCEL Runnables:

The core architectural design of LCEL relies on composing runnables via the pipe operator: $R_1 \mid R_2 \mid R_3$.

  1. Formulate the Category of Runnables $\mathcal{C}_{\text{Runnable}}$:
    • Define the Objects of $\mathcal{C}_{\text{Runnable}}$.
    • Define the Morphisms (Arrows) $f: A \to B$ in $\mathcal{C}_{\text{Runnable}}$.
  2. Prove that the composition operator $\mid$ satisfies the two foundational axioms of Category Theory:
    • Associativity: $(f \mid g) \mid h = f \mid (g \mid h)$ for all composable runnables.
    • Identity: For every object $A$, there exists an identity morphism $\text{id}_A$ such that for any $f: A \to B$, $\text{id}_A \mid f = f \mid \text{id}_B = f$. Identify the LangChain primitive that implements $\text{id}_A$.
  3. Prove that asynchronous streaming runnables form a Kleisli Category over the AsyncStream Monad: $$M(X) = \text{AsyncIterator}[X]$$
✓ Complete Category-Theoretic Proof

Part 1: Definition of the Category $\mathcal{C}_{\text{Runnable}}$:
A category $\mathcal{C}$ consists of objects, morphisms, an identity morphism for each object, and an associative composition law:

  1. Objects $\text{Ob}(\mathcal{C}_{\text{Runnable}})$: The objects are data types/schemas (e.g. `str`, `dict`, `ChatMessage`, `BaseModel`, `List[Document]`).
  2. Morphisms $\text{Hom}(A, B)$: For any pair of types $A, B$, a morphism $f \in \text{Hom}(A, B)$ is an instance of `Runnable[A, B]` encapsulating an invocation mapping $f: A \to B$ (or async mapping $f: A \to \text{Future}[B]$).

Part 2: Verification of Category Axioms:
1. Associativity Proof:
Let $f \in \text{Hom}(A, B)$, $g \in \text{Hom}(B, C)$, and $h \in \text{Hom}(C, D)$. The composition $(f \mid g): A \to C$ is defined by: $$(f \mid g)(x) = g(f(x))$$ Evaluating $((f \mid g) \mid h)$ on input $x \in A$: $$((f \mid g) \mid h)(x) = h((f \mid g)(x)) = h(g(f(x)))$$ Evaluating $(f \mid (g \mid h))$ on input $x \in A$: $$(f \mid (g \mid h))(x) = (g \mid h)(f(x)) = h(g(f(x)))$$ Since $((f \mid g) \mid h)(x) = (f \mid (g \mid h))(x)$ for all $x \in A$: $$(f \mid g) \mid h = f \mid (g \mid h) \quad \blacksquare$$ Composition is strictly associative! This allows engineers to nest, split, and regroup sub-chains arbitrarily without changing execution semantics.

2. Identity Morphism:
For any type object $A$, define $\text{id}_A(x) = x$. In LangChain, this morphism is implemented by RunnablePassthrough() (or RunnableLambda(lambda x: x)). For any $f \in \text{Hom}(A, B)$ and $x \in A$: $$(\text{id}_A \mid f)(x) = f(\text{id}_A(x)) = f(x)$$ $$(f \mid \text{id}_B)(x) = \text{id}_B(f(x)) = f(x)$$ Thus $\text{id}_A \mid f = f \mid \text{id}_B = f$. Identity holds. $\blacksquare$

Part 3: Streaming as a Kleisli Category:
In streaming execution, each component does not return a single object $B$; it returns an asynchronous stream $M(B) = \text{AsyncIterator}[B]$. The functor $M$ is the Monad with:

  • Unit (Return): $\eta(x) = \text{async\_stream\_of}(x)$.
  • Bind ($\star$): Given a stream $s \in M(A)$ and a mapping $g: A \to M(B)$, the bind operation flattens intermediate token chunks asynchronously: $$(s \star g) = \text{async for } chunk \text{ in } s: \text{async for } out \text{ in } g(chunk): \text{yield } out$$
LCEL pipes seamlessly compose token-level streaming generators across transformers and parsers. $\blacksquare$

Problem 5.7.6 Tier 3: FAANG / Research Lab Proof Amazon Web Services Meta

Mathematical Proof: Tail Latency Distribution and Availability of Fallback Cascades:

In high-availability enterprise AI systems, an LCEL chain is configured with a primary model $\mathcal{M}_1$ and a fallback model $\mathcal{M}_2$:

$$\text{chain} = \mathcal{M}_1.\text{with\_fallbacks}([\mathcal{M}_2])$$

Let $E_1$ and $E_2$ be independent failure events (timeout or HTTP 5xx) with failure probabilities $p_1$ and $p_2$. Latency of each model given success follows exponential distributions with parameters $\lambda_1$ and $\lambda_2$ (mean latencies $\mu_1 = 1/\lambda_1$ and $\mu_2 = 1/\lambda_2$). A timeout threshold $\tau$ is set on $\mathcal{M}_1$.

  1. Prove that the overall system failure probability is $p_{\text{system}} = p_1 p_2$ (assuming independent failure modes). Calculate system availability for $p_1 = 0.05$ (95% SLA) and $p_2 = 0.02$ (98% SLA).
  2. Derive the cumulative distribution function (CDF) of the system response latency $F_{\text{sys}}(t)$ for $t > \tau$.
✓ Complete Probability & Reliability Proof

Part 1: Overall System Availability:
The system fails if and only if both the primary model fails AND the fallback model fails: $$p_{\text{system}} = \mathbb{P}(E_1 \cap E_2)$$ Assuming provider independence (e.g. $\mathcal{M}_1$ is OpenAI in US-East and $\mathcal{M}_2$ is self-hosted vLLM in AWS EU-West): $$p_{\text{system}} = p_1 \times p_2$$ Plugging in $p_1 = 0.05$ and $p_2 = 0.02$: $$p_{\text{system}} = 0.05 \times 0.02 = 0.0010 = \mathbf{0.10\% \text{ Failure Rate}}$$ System availability: $$\text{Availability} = 1 - p_{\text{system}} = 1 - 0.0010 = \mathbf{99.90\% \text{ Three-Nines SLA!}}$$ A fallback cascade elevates a 95% SLA service to an enterprise-grade 99.9% availability service!

Part 2: Derivation of Latency CDF $F_{\text{sys}}(t)$ for $t > \tau$:
For $t > \tau$, the primary model either succeeded before timeout $\tau$ (probability $(1 - p_1)(1 - e^{-\lambda_1 \tau})$), or timed out at $\tau$, triggering the fallback model which must complete in the remaining time $t - \tau$: $$\mathbb{P}(\text{Fallback succeeds in time } t - \tau) = 1 - e^{-\lambda_2 (t - \tau)}$$ The probability of invoking the fallback branch is $P_{\text{trigger}} = p_1 + (1 - p_1) e^{-\lambda_1 \tau}$. Therefore, for $t > \tau$: $$F_{\text{sys}}(t) = \mathbb{P}(\mathcal{M}_1 \le \tau) + P_{\text{trigger}} \times (1 - p_2) \left( 1 - e^{-\lambda_2 (t - \tau)} \right)$$ $$F_{\text{sys}}(t) = (1 - p_1)(1 - e^{-\lambda_1 \tau}) + \left[ p_1 + (1 - p_1)e^{-\lambda_1 \tau} \right](1 - p_2)(1 - e^{-\lambda_2 (t - \tau)}) \quad \blacksquare$$

Problem 5.7.7 Tier 4: Conceptual Trap MCQ Meta Uber

Conceptual Trap: The "Sync-Inside-Async" Event Loop Blocking Disaster:

An engineer builds an asynchronous high-throughput FastAPI service using an LCEL pipeline. Inside the chain, they add a custom RunnableLambda that logs analytics to a PostgreSQL database:

def log_to_postgres(data: dict) -> dict:
    import psycopg2 # Synchronous blocking database driver
    conn = psycopg2.connect("...")
    cursor = conn.cursor()
    cursor.execute("INSERT INTO audit_logs VALUES (%s)", (str(data),))
    conn.commit()
    return data

chain = prompt | llm | RunnableLambda(log_to_postgres) | parser

During load testing at 500 concurrent requests/second, the service's throughput collapses from 500 req/s to under 4 req/s, and all WebSocket connections freeze. What is the precise architectural failure mechanism?

  • (A) PostgreSQL does not support string parsing from Pydantic schemas.
  • (B) The synchronous, blocking socket I/O inside psycopg2 hijacks the single-threaded Python asyncio event loop, preventing all other concurrent coroutines from scheduling until the database round-trip finishes.
  • (C) RunnableLambda automatically disables GPU acceleration in PyTorch.
  • (D) The pipe operator | only works with mathematical matrices, not database connections.
✓ Complete Distractor Analysis & Architectural Rationale

Correct Answer: (B)

Exhaustive Distractor Analysis:

  • Why (B) is Correct: Python's asyncio runs on a single OS thread that juggles thousands of non-blocking I/O sockets. When a synchronous blocking function (like psycopg2, requests.get(), or time.sleep()) is invoked directly inside an async pipeline, it holds the CPU thread captive during network socket waiting. The event loop cannot yield control to any other waiting coroutine. If one database write takes 250 ms, the entire server can handle at most 4 requests per second! The production solution is to use async drivers (e.g. asyncpg) with ainvoke() or offload synchronous blocking code to a separate thread pool using run_in_executor or asyncio.to_thread(log_to_postgres).
  • Why (A) is Incorrect: PostgreSQL easily stores strings; this is an asynchronous event loop starvation bug, not an SQL syntax error.
  • Why (C) is Incorrect: RunnableLambda is a CPU orchestration wrapper; it has no negative effect on PyTorch CUDA execution.
  • Why (D) is Incorrect: In LCEL, | is overloaded via Python's __or__ dunder method on Runnable objects to compose arbitrary functions.

from pydantic import BaseModel, Field

class MockRunnable:
    """Runnable abstraction illustrating LCEL operator composition and streaming."""
    def __init__(self, func):
        self.func = func

    def __or__(self, other):
        """Implements Unix-style pipe syntax: A | B"""
        return MockRunnable(lambda x: other.invoke(self.func(x)))

    def invoke(self, x):
        return self.func(x)

class ContractSummary(BaseModel):
    contract_title: str = Field(description="Formal name of legal contract")
    parties_involved: List[str] = Field(description="Names of contracting entities")
    total_value_usd: float = Field(description="Monetary consideration in USD")
    governing_law: str = Field(description="State or country jurisdiction")

def mock_prompt_template(inputs: dict) -> str:
    return f"Extract structured legal entities from text: {inputs['text']}"

def mock_llm_json_call(prompt: str) -> dict:
    # Simulates JSON function-calling schema enforcement from frontier LLM
    return {
        "contract_title": "Master Cloud Services Agreement",
        "parties_involved": ["Acme Corp", "Apex Cloud Ltd"],
        "total_value_usd": 250000.00,
        "governing_law": "Delaware"
    }

def pydantic_parser(data: dict) -> ContractSummary:
    return ContractSummary(**data)

if __name__ == "__main__":
    prompt_runnable = MockRunnable(mock_prompt_template)
    llm_runnable = MockRunnable(mock_llm_json_call)
    parser_runnable = MockRunnable(pydantic_parser)

    # Declarative LCEL Composition: Prompt | Model | Parser
    pipeline = prompt_runnable | llm_runnable | parser_runnable

    raw_input = {"text": "Acme Corp agrees to pay Apex Cloud Ltd USD 250,000 under Delaware law."}
    result = pipeline.invoke(raw_input)

    print("--- LCEL Pipeline Execution & Pydantic Validation ---")
    print(f"Contract Title : {result.contract_title}")
    print(f"Parties        : {', '.join(result.parties_involved)}")
    print(f"Total Value    : ${result.total_value_usd:,.2f}")
    print(f"Governing Law  : {result.governing_law}")
    assert isinstance(result, ContractSummary)
    print("[SUCCESS] Production LCEL Pipeline & Pydantic Schema Validated.")
