1. The PyTorch Autograd Engine & Custom Autograd Functions

PyTorch's automatic differentiation engine operates on a dynamically constructed Directed Acyclic Graph (DAG) of Node (or Function) objects. Unlike static frameworks that compile a fixed execution graph ahead of time, PyTorch uses a tape-based automatic differentiation system (Reverse-Mode AD): during the forward pass, operations on tensors with requires_grad=True dynamically construct execution nodes that record both the mathematical operation and the input/output tensors necessary for backpropagation.

1.1 Leaf vs. Non-Leaf Tensors and the Gradient DAG

Every tensor in PyTorch has two fundamental topological properties within the graph:

  • Leaf Tensors (tensor.is_leaf == True): Tensors explicitly instantiated by the user (such as model weights $\mathbf{W}$, biases $\mathbf{b}$, or raw inputs $\mathbf{x}$) that are not the result of an operation recorded by autograd. By default, PyTorch only accumulates gradients in leaf tensors (tensor.grad).
  • Non-Leaf Tensors (tensor.is_leaf == False): Intermediate activations resulting from operations (e.g., $\mathbf{z} = \mathbf{W}\mathbf{x} + \mathbf{b}$, $\mathbf{a} = \sigma(\mathbf{z})$). Their grad_fn attribute points to the backward operator (e.g., <AddBackward0>, <ReluBackward0>). To conserve VRAM, PyTorch automatically discards gradients of non-leaf tensors after backpropagation unless tensor.retain_grad() is explicitly invoked!

1.2 Implementing Custom Autograd Functions (torch.autograd.Function)

When implementing novel operators (e.g., fused attention kernels, specialized activation functions, or custom quantization passes), subclassing torch.autograd.Function allows exact control over forward caching and backward gradient computation:

import torch

class FusedClippedLinear(torch.autograd.Function):
    @staticmethod
    def forward(ctx, x, weight, bias, clip_val=2.0):
        """
        Forward: Computes z = clamp(x @ weight.T + bias, -clip_val, clip_val)
        ctx: Context object to stash tensors or non-tensor attributes for backward
        """
        z_unclipped = torch.addmm(bias, x, weight.t())
        z_clipped = torch.clamp(z_unclipped, -clip_val, clip_val)
        
        # Save tensors needed for backward pass
        ctx.save_for_backward(x, weight, z_unclipped)
        ctx.clip_val = clip_val # Save scalar attributes
        return z_clipped

    @staticmethod
    def backward(ctx, grad_output):
        """
        Backward: Receives dL/dz_clipped, computes dL/dx, dL/dweight, dL/dbias, dL/dclip_val
        """
        x, weight, z_unclipped = ctx.saved_tensors
        clip_val = ctx.clip_val

        # Subgradient mask for clamp: 1 if |z_unclipped| <= clip_val else 0
        mask = (z_unclipped >= -clip_val) & (z_unclipped <= clip_val)
        grad_z = grad_output * mask.to(grad_output.dtype)

        # Matrix calculus chain rule
        grad_x = grad_z.mm(weight)
        grad_weight = grad_z.t().mm(x)
        grad_bias = grad_z.sum(dim=0)
        grad_clip_val = None # Non-differentiable hyperparameter returns None

        return grad_x, grad_weight, grad_bias, grad_clip_val

2. PyTorch CUDA Memory Management: Inside the Caching Allocator

A frequent point of confusion among engineers is why calling nvidia-smi reveals 22 GB of allocated VRAM while PyTorch's torch.cuda.memory_allocated() reports only 6 GB. Understanding the PyTorch Caching Allocator is critical to preventing out-of-memory (OOM) failures.

2.1 Physical Allocation vs. Cached Memory Pools

Invoking the CUDA driver API cudaMalloc() and cudaFree() forces a kernel synchronization barrier across all CPU and GPU threads, introducing massive latency overhead (often tens of milliseconds per call). To achieve real-time performance, PyTorch employs a custom Caching Allocator:

  • Allocated Memory (torch.cuda.memory_allocated()): The exact byte volume currently occupied by active tensor storage buffers.
  • Reserved / Cached Memory (torch.cuda.memory_reserved()): The total physical VRAM held by PyTorch's memory manager. When a tensor is freed in Python via reference counting or del tensor, its memory is not returned to the NVIDIA driver via cudaFree(); instead, it is returned to PyTorch's internal block pool for immediate reuse.
  • The Danger of torch.cuda.empty_cache(): This function flushes all cached, unallocated memory back to the driver. Calling it inside your training loop forces continuous cudaMalloc/cudaFree driver synchronization, destroying throughput by up to $50\%$. It should only be used during graceful error handling or epoch boundary mode switches.

3. Eradicating the Host-to-Device Data Bottleneck

In production training, the most expensive mistake an engineer can make is GPU Starvation: a $30,000 NVIDIA H100 GPU sitting 80% idle because the single-threaded CPU cannot decode images or tokenize text fast enough to feed the PCIe bus.

The Three Pillars of High-Throughput PyTorch Data Loading

  1. Multiprocessing Workers (num_workers > 0): Spawns separate OS background worker processes to deserialize, augment, and batch data asynchronously while the GPU computes the previous forward/backward pass.
  2. Pinned (Page-Locked) Memory (pin_memory=True): By default, operating systems allocate virtual memory in pageable host RAM, requiring CPU involvement during PCIe copy. Pinned memory locks memory into physical host RAM, enabling asynchronous Direct Memory Access (DMA) over the PCIe bus without touching the CPU.
  3. Non-Blocking Transfers (non_blocking=True): Asynchronously transfers tensors to GPU VRAM concurrently with CUDA stream computation: $$\text{inputs} = \text{inputs.to}(\text{device}=\text{"cuda"}, \text{non\_blocking}=\text{True})$$

4. Automatic Mixed Precision (AMP) & The GradScaler

Training in full FP32 (4 bytes per number) wastes 50% of memory and leaves NVIDIA Tensor Cores underutilized. Automatic Mixed Precision (AMP) runs compute-heavy matrix multiplications (linear projections, convolutions) in fast 16-bit precision (FP16 or BF16) while keeping numerically sensitive operations (softmax, loss reductions) in FP32.

🚨 The FP16 Underflow Trap & Dynamic Loss Scaling

Standard IEEE 754 16-bit float (FP16) allocates only 5 bits to the exponent, giving it a minimum positive normal representable value of $2^{-14} \approx 6.1035 \times 10^{-5}$ (and a subnormal minimum of $2^{-24} \approx 5.96 \times 10^{-8}$). In deep networks, activation gradients are often smaller than $10^{-6}$. In standard FP16, these gradients underflow to exact zero!

The GradScaler mathematically solves this through dynamic loss scaling:

  1. Before backpropagation, the scalar loss is multiplied by a large scale factor $S$ (initial default $S_0 = 2^{16} = 65,536$): $$\mathcal{L}_{\text{scaled}} = S \cdot \mathcal{L}$$
  2. By the chain rule of differentiation, all backpropagated gradients are scaled by $S$: $$\mathbf{g}_{\text{scaled}} = \frac{\partial \mathcal{L}_{\text{scaled}}}{\partial \mathbf{W}} = S \cdot \frac{\partial \mathcal{L}}{\partial \mathbf{W}} = S \cdot \mathbf{g}$$ This shifts tiny gradients into the safe, non-zero FP16 dynamic range!
  3. Before the optimizer step, gradients are unscaled back: $\mathbf{g} = \mathbf{g}_{\text{scaled}} / S$.
  4. Dynamic Scale Adjustment: If an overflow (inf or nan) is detected in any gradient buffer, the optimizer step is discarded (skipped), and the scale factor is halved: $$S \leftarrow S \times \text{backoff\_factor} \quad (\text{typically } S \leftarrow S / 2)$$ If no overflows occur for $N_{\text{growth}}$ consecutive steps (typically 2000 steps), the scale factor is doubled: $$S \leftarrow S \times \text{growth\_factor} \quad (\text{typically } S \leftarrow S \times 2)$$

5. Gradient Accumulation & Gradient Checkpointing

Large batch sizes ($B = 1024$ or $4096$) stabilize optimizer variance and improve generalization. However, fitting $1024$ high-resolution images or 4,096-token sequences into consumer GPU VRAM causes immediate CUDA Out of Memory (OOM) crashes.

Gradient Accumulation mathematically simulates large batches on small hardware: we divide batch $B$ into $K$ micro-batches of size $B_{\text{micro}} = B / K$, running forward and backward passes while accumulating gradients into existing .grad buffers before calling optimizer.step():

$$\mathbf{g}_{\text{total}} = \frac{1}{K} \sum_{k=1}^K \nabla_\mathbf{w} \mathcal{L}_k(\mathbf{w})$$

Gradient Checkpointing (Activation Recomputation): Standard backprop stores all intermediate activation tensors from the forward pass in VRAM. Gradient checkpointing discards intermediate activations during forward evaluation and recomputes them on-the-fly during the backward pass. This reduces activation VRAM from $O(L)$ to $O(\sqrt{L})$ across $L$ layers at the cost of merely $\approx 33\%$ additional forward compute FLOPs!

6. Distributed Training: DataParallel vs. DistributedDataParallel (DDP)

Scaling deep learning across multiple GPUs requires understanding the architectural divide between PyTorch's legacy nn.DataParallel (DP) and production nn.parallel.DistributedDataParallel (DDP):

Feature torch.nn.DataParallel (DP) torch.nn.parallel.DistributedDataParallel (DDP)
Architecture Single-process, multi-threaded Multi-process (1 dedicated OS process per GPU)
Python GIL Bottleneck Severe: all threads blocked by single Python GIL Zero: independent Python processes completely bypass GIL
GPU 0 Load Imbalance Massive: GPU 0 gathers all outputs, computes loss, scatters gradients Zero: perfectly symmetric, each GPU computes its own loss

6.1 The Ring All-Reduce Algorithm & Communication Efficiency

In DDP, synchronizing gradients across $N$ GPUs without a centralized parameter server is achieved via the Ring All-Reduce communication algorithm. Gradients of size $M$ bytes are partitioned into $N$ equal chunks of size $M/N$. The $N$ GPUs are arranged in a logical ring where GPU $i$ only transmits to GPU $(i+1) \pmod N$ and receives from GPU $(i-1) \pmod N$.

The algorithm executes in two successive phases:

  1. Scatter-Reduce Phase: Over $N-1$ steps, each GPU transmits a chunk and receives a chunk, summing received values into its local buffer. After $N-1$ steps, each GPU holds the globally summed gradient for exactly one chunk of size $M/N$. Data sent per GPU: $$(N-1) \times \frac{M}{N} = \frac{N-1}{N} M \text{ bytes}$$
  2. Allgather Phase: Over $N-1$ steps, the fully reduced chunks are circulated around the ring so that every GPU acquires all $N$ reduced chunks. Data sent per GPU: $$(N-1) \times \frac{M}{N} = \frac{N-1}{N} M \text{ bytes}$$

Total data transmitted per GPU:

$$\text{Total Transmitted Volume} = 2 \times \frac{N-1}{N} M \text{ bytes}$$

Notice that as $N \to \infty$, the total transmitted data per GPU approaches $2M$, which is completely independent of the number of GPUs $N$! Contrast this with a naive parameter server where the central master must transmit and receive $2(N-1)M$ bytes, causing total network collapse as $N$ grows.

QUESTION (Mathematical Proof of Ring All-Reduce Communication Complexity): Consider a distributed cluster of $N$ GPUs synchronizing a gradient tensor of size $M$ bytes.

  2. Prove that as $N \to \infty$, the communication volume per GPU is strictly bounded by $2M$, demonstrating that Ring All-Reduce is bandwidth-optimal.

✓ Complete First-Principles Mathematical Proof

Step 1: Derivation of Ring All-Reduce Transmitted Volume: Partition the total gradient tensor $\mathbf{g}$ of size $M$ bytes into $N$ disjoint chunks of equal size: $$\text{Chunk Size } S = \frac{M}{N}$$ Arrange the $N$ GPUs in a logical directed cycle: $\text{GPU}_0 \to \text{GPU}_1 \to \dots \to \text{GPU}_{N-1} \to \text{GPU}_0$. Phase 1: Scatter-Reduce: At step $k \in \{1, 2, \dots, N-1\}$:

  • Each GPU $i$ transmits chunk index $(i - k) \pmod N$ of size $\frac{M}{N}$ to its right neighbor $(i+1) \pmod N$.
  • Concurrently, GPU $i$ receives chunk $(i - k - 1) \pmod N$ from its left neighbor and sums it into its local accumulator.
Since there are $N-1$ steps, each GPU transmits: $$\text{Data Transmitted in Phase 1} = (N-1) \times \frac{M}{N} = \frac{N-1}{N} M \text{ bytes}$$ At the conclusion of Phase 1, each GPU $i$ holds the complete, fully reduced global sum for exactly one chunk (chunk $i$). Phase 2: Allgather: The fully reduced chunks must now be broadcast to all remaining $N-1$ GPUs. At step $k \in \{1, 2, \dots, N-1\}$:
  • Each GPU $i$ transmits the fully reduced chunk it received in the prior step to GPU $(i+1) \pmod N$.
This requires another $N-1$ steps, where each GPU sends a chunk of size $\frac{M}{N}$ per step: $$\text{Data Transmitted in Phase 2} = (N-1) \times \frac{M}{N} = \frac{N-1}{N} M \text{ bytes}$$ Summing Phase 1 and Phase 2: $$\text{Total Volume per GPU} = \frac{N-1}{N} M + \frac{N-1}{N} M = \mathbf{2 \frac{N-1}{N} M \text{ bytes}} \quad \blacksquare$$

Step 2: Asymptotic Limit as $N \to \infty$: Taking the mathematical limit as the cluster scales: $$\lim_{N \to \infty} 2 \left(\frac{N-1}{N}\right) M = 2 \lim_{N \to \infty} \left(1 - \frac{1}{N}\right) M = 2(1 - 0) M = \mathbf{2M}$$ Significance: The network communication time per training step is: $$T_{\text{comm}} = \frac{2 \frac{N-1}{N} M}{B_{\text{link}}} \approx \frac{2M}{B_{\text{link}}}$$ where $B_{\text{link}}$ is the interconnect bandwidth (e.g., 900 GB/s on NVLink). The communication duration remains strictly constant whether training on 8 GPUs or 8,192 GPUs!

Step 3: Comparison with Centralized Parameter Server (PS): In a Parameter Server architecture with $N$ worker nodes and 1 central server:

  • Each worker sends its local gradient of size $M$ to the server: Server receives $N \times M$ bytes.
  • The server aggregates gradients and broadcasts updated weights of size $M$ back to all $N$ workers: Server transmits $N \times M$ bytes.
Total data transferred through the Parameter Server's network interface: $$\text{PS Volume} = 2 N M = O(N \cdot M)$$ As $N$ increases, the central server's network bandwidth saturates instantly. For $N = 64$ and $M = 4 \text{ GB}$, PS requires transferring $2 \times 64 \times 4 = 512 \text{ GB}$ per step through one node, causing complete cluster paralysis, whereas Ring All-Reduce requires only $2 \times \frac{63}{64} \times 4 \approx 7.88 \text{ GB}$ per GPU!

Problem 3.6.6 Hard OpenAI Anthropic

QUESTION (Equivalence and Invariance of Gradient Accumulation): An engineer splits a target batch $\mathcal{B}$ of size $B$ into $K$ disjoint micro-batches $\mathcal{B}_1, \dots, \mathcal{B}_K$, each of size $B_{\text{micro}} = B/K$.

  1. Prove that for Standard Stochastic Gradient Descent (SGD), accumulating gradients by computing $\mathcal{L}_k = \frac{1}{K} \frac{1}{B_{\text{micro}}} \sum_{i \in \mathcal{B}_k} \ell(f(\mathbf{x}_i), y_i)$ produces a parameter update that is mathematically identical to updating on the full batch $B$ in a single step.
  2. Prove why this exact equivalence fails if the architecture contains torch.nn.BatchNorm2d layers.
  3. Explain why dividing each micro-batch loss by $K$ (i.e. loss = criterion(...) / accumulation_steps) before calling loss.backward() is required, and what catastrophic optimizer pathology occurs if an engineer omits the division by $K$.
✓ Complete Proof & Invariance Analysis

Step 1: SGD Mathematical Equivalence Proof: Let the loss on the full batch $\mathcal{B} = \bigcup_{k=1}^K \mathcal{B}_k$ of size $B = K \cdot B_{\text{micro}}$ be: $$\mathcal{L}(\mathbf{w}) = \frac{1}{B} \sum_{i \in \mathcal{B}} \ell_i(\mathbf{w})$$ The true gradient is: $$\mathbf{g}_{\text{full}} = \nabla_\mathbf{w} \mathcal{L}(\mathbf{w}) = \frac{1}{B} \sum_{i \in \mathcal{B}} \nabla_\mathbf{w} \ell_i(\mathbf{w})$$ In gradient accumulation, for each micro-batch $k \in \{1, \dots, K\}$, we define the micro-batch loss scaled by $1/K$: $$\tilde{\mathcal{L}}_k(\mathbf{w}) = \frac{1}{K} \left(\frac{1}{B_{\text{micro}}} \sum_{i \in \mathcal{B}_k} \ell_i(\mathbf{w})\right) = \frac{1}{K \cdot B_{\text{micro}}} \sum_{i \in \mathcal{B}_k} \ell_i(\mathbf{w}) = \frac{1}{B} \sum_{i \in \mathcal{B}_k} \ell_i(\mathbf{w})$$ Because differentiation is a linear operator ($\nabla \sum = \sum \nabla$), when PyTorch accumulates gradients in w.grad += ... across $K$ backward passes without zeroing: $$\mathbf{g}_{\text{accum}} = \sum_{k=1}^K \nabla_\mathbf{w} \tilde{\mathcal{L}}_k(\mathbf{w}) = \sum_{k=1}^K \left(\frac{1}{B} \sum_{i \in \mathcal{B}_k} \nabla_\mathbf{w} \ell_i(\mathbf{w})\right) = \frac{1}{B} \sum_{k=1}^K \sum_{i \in \mathcal{B}_k} \nabla_\mathbf{w} \ell_i(\mathbf{w}) = \frac{1}{B} \sum_{i \in \mathcal{B}} \nabla_\mathbf{w} \ell_i(\mathbf{w}) = \mathbf{g}_{\text{full}}$$ The accumulated gradient $\mathbf{g}_{\text{accum}}$ is identical to $\mathbf{g}_{\text{full}}$ to the last floating-point bit! $\quad \blacksquare$

Step 2: Breakdown Under Batch Normalization: In Batch Normalization, the forward activation for sample $i$ depends non-linearly on the mean and variance computed across the active micro-batch: $$\mu_k = \frac{1}{B_{\text{micro}}} \sum_{j \in \mathcal{B}_k} x_j, \quad \sigma_k^2 = \frac{1}{B_{\text{micro}}} \sum_{j \in \mathcal{B}_k} (x_j - \mu_k)^2$$ $$\hat{x}_i = \frac{x_i - \mu_k}{\sqrt{\sigma_k^2 + \epsilon}}$$ In a single large batch of size $B$, the statistics $\mu_{\text{full}}$ and $\sigma^2_{\text{full}}$ are computed over all $B$ samples. Since: $$\frac{x_i - \mu_k}{\sqrt{\sigma_k^2 + \epsilon}} \ne \frac{x_i - \mu_{\text{full}}}{\sqrt{\sigma_{\text{full}}^2 + \epsilon}}$$ the forward outputs differ: $f_{\mathcal{B}_k}(\mathbf{x}_i) \ne f_\mathcal{B}(\mathbf{x}_i)$. Consequently, the individual sample gradients $\nabla \ell_i$ are evaluated at completely different activation values! Therefore, gradient accumulation with Batch Normalization does not equal full-batch training (unless replaced by SyncBatchNorm or LayerNorm / RMSNorm).

Step 3: The Pathology of Omitting Division by $K$: If the engineer writes loss = criterion(...) without dividing by $K$, each backward call computes $\frac{1}{B_{\text{micro}}} \sum_{i \in \mathcal{B}_k} \nabla \ell_i$. Summing these over $K$ steps yields: $$\mathbf{g}_{\text{unscaled}} = \sum_{k=1}^K \frac{1}{B_{\text{micro}}} \sum_{i \in \mathcal{B}_k} \nabla \ell_i = \frac{1}{B/K} \sum_{i \in \mathcal{B}} \nabla \ell_i = K \cdot \mathbf{g}_{\text{full}}$$ The accumulated gradient is $K$ times too large! In SGD, this unintentionally scales the effective learning rate by $K$: $\eta_{\text{eff}} = K \cdot \eta$, typically causing explosive gradient divergence, loss blowup to NaN, and ruined training runs.

Problem 3.6.7 Medium Stripe Tesla

QUESTION (The Non-Leaf Tensor Gradient Trap): An ML engineer writes the following PyTorch code to inspect intermediate gradients during backpropagation:

import torch

x = torch.randn(4, 8, requires_grad=True)
W = torch.randn(8, 16, requires_grad=True)
z = torch.matmul(x, W) # Intermediate activation
y = z.relu()
loss = y.sum()
loss.backward()

print("x.grad:", x.grad is not None)
print("W.grad:", W.grad is not None)
print("z.grad:", z.grad is not None)

What is the exact output printed by this script, and which explanation correctly describes PyTorch's internal autograd behavior?

  • (A) True, True, True — All tensors derived from requires_grad=True inputs retain gradients in their .grad attribute.
  • (B) True, True, False — z is a non-leaf tensor; PyTorch computes its gradient during backward pass to apply the chain rule but immediately frees the memory buffer, leaving z.grad = None unless z.retain_grad() was called.
  • (C) False, False, True — Gradients are only populated at the final activation z before ReLU.
  • (D) RuntimeError — PyTorch crashes because intermediate tensor z cannot be differentiated when ReLU is applied in-place.
✓ Correct Answer: (B)

Exhaustive Distractor Analysis:

  • (B) is CORRECT: In PyTorch's autograd DAG, x and W were created directly by the user, so x.is_leaf == True and W.is_leaf == True. As leaf nodes, their gradients are permanently stored in x.grad and W.grad. In contrast, z is produced by torch.matmul(x, W), making it a non-leaf node (z.is_leaf == False). While the autograd engine computes $\frac{\partial \mathcal{L}}{\partial \mathbf{z}} = \frac{\partial \mathcal{L}}{\partial \mathbf{y}} \odot \mathbf{1}_{\mathbf{z} > 0}$ during the backward pass to compute gradients for x and W, it immediately deallocates z's gradient buffer once upstream dependencies are satisfied. Thus, z.grad evaluates to None! To retain it, the user must call z.retain_grad() before loss.backward().
  • (A) is INCORRECT: Assumes PyTorch retains gradients for all intermediate tensors. If PyTorch kept gradients for every intermediate layer in a 100-layer ResNet or Transformer, VRAM consumption would triple, causing immediate OOM.
  • (C) is INCORRECT: Leaf tensors x and W always receive gradients if they have requires_grad=True.
  • (D) is INCORRECT: y = z.relu() is an out-of-place operation (not z.relu_()), so no RuntimeError occurs.

Problem 3.6.8 Hard Meta Databricks

QUESTION (The DataParallel GPU 0 Memory Imbalance Pathology): An engineer runs training on a 4-GPU server using model = torch.nn.DataParallel(model) with batch size $B = 128$ (32 samples per GPU). During the very first backward step, GPU 0 crashes with CUDA Out of Memory, while GPU 1, 2, and 3 report less than 50% VRAM utilization. Which of the following statements rigorously identifies the architectural root cause and the production remedy?

  • (A) GPU 0 is running the operating system display server (Xorg/Wayland), which consumes 18 GB of VRAM; the remedy is disabling the display driver.
  • (B) nn.DataParallel uses a master-worker architecture where GPU 0 replicates model weights to all GPUs, gathers all forward outputs to GPU 0, evaluates the loss scalar on GPU 0, scatters loss to all GPUs, and gathers all gradients back to GPU 0 to execute optimizer.step(). GPU 0 thus bears the entire memory overhead of output gathering, loss reduction, and optimizer state buffers. The remedy is migrating to DistributedDataParallel (DDP), which is completely decentralized and symmetric.
  • (C) PyTorch DataParallel defaults to FP64 precision on GPU 0 while using FP16 on worker GPUs; the remedy is passing torch.set_default_dtype(torch.float16).
  • (D) The CUDA driver creates a deadlock between PCIe slots 0 and 1; the remedy is running with CUDA_LAUNCH_BLOCKING=1.
✓ Correct Answer: (B)

Exhaustive Systems Architecture Analysis:

  • (B) is CORRECT: torch.nn.DataParallel is a single-process multi-threaded wrapper. In DP, the primary GPU (GPU 0 by default) acts as the centralized coordinator:
    1. Forward Scatter: GPU 0 scatters micro-batches to GPUs 0, 1, 2, 3 and broadcasts model weights.
    2. Forward Gather: All output activation tensors from GPUs 0, 1, 2, 3 are gathered back onto GPU 0. If batch size is 128 with large sequence lengths or logits, GPU 0 must store the entire gathered tensor of all 128 samples!
    3. Loss Computation: The loss function is evaluated on GPU 0.
    4. Backward Gather: During backpropagation, all gradients are gathered onto GPU 0. Furthermore, the optimizer (e.g., AdamW) only lives on GPU 0, meaning all 16 bytes/parameter of AdamW states reside solely in GPU 0 VRAM!
    This causes massive memory asymmetry where GPU 0 carries up to $3\times$ the VRAM burden of other GPUs. Switching to DistributedDataParallel (DDP) spawns one independent OS process per GPU, where each GPU independently maintains its own optimizer and model replica, eliminating all centralized gathering via peer-to-peer Ring All-Reduce!
  • (A) is INCORRECT: Display managers typically occupy 100–300 MB of VRAM on headless server racks, nowhere near enough to cause multi-gigabyte disparity.
  • (C) is INCORRECT: DataParallel never silently alters tensor precision across GPUs.
  • (D) is INCORRECT: CUDA_LAUNCH_BLOCKING=1 forces synchronous CUDA kernel launches for debugging stack traces; it does not alter memory allocation patterns or resolve memory imbalances.

Code Lab 3.6 — Production PyTorch Training Pipeline

🔗 View in GitHub: part3_neural_networks/ch36_pytorch_production/train_pipeline.py

import os
import signal
import torch
import torch.nn as nn
from torch.cuda.amp import autocast, GradScaler

class ProductionTrainer:
    def __init__(self, model, optimizer, criterion, device="cuda", accum_steps=4):
        self.model = model.to(device)
        self.optimizer = optimizer
        self.criterion = criterion
        self.device = device
        self.accum_steps = accum_steps
        self.scaler = GradScaler()
        self.interrupted = False

        # Register graceful termination handler for spot instances
        signal.signal(signal.SIGTERM, self._handle_sigterm)
        signal.signal(signal.SIGINT, self._handle_sigterm)

    def _handle_sigterm(self, signum, frame):
        print("\n[ALERT] Received termination signal! Finishing active step & saving state...")
        self.interrupted = True

    def train_epoch(self, dataloader, epoch=0):
        self.model.train()
        self.optimizer.zero_grad()
        running_loss = 0.0

        for step, (inputs, targets) in enumerate(dataloader):
            # Asynchronous DMA Host-to-Device transfer
            inputs = inputs.to(self.device, non_blocking=True)
            targets = targets.to(self.device, non_blocking=True)

            # 1. Forward pass under Automatic Mixed Precision
            with autocast(dtype=torch.float16):
                outputs = self.model(inputs)
                loss = self.criterion(outputs, targets) / self.accum_steps

            # 2. Scaled backward pass (protects against FP16 underflow)
            self.scaler.scale(loss).backward()
            running_loss += loss.item() * self.accum_steps

            # 3. Optimizer step at accumulation boundaries
            if (step + 1) % self.accum_steps == 0:
                # Unscale gradients prior to gradient norm clipping
                self.scaler.unscale_(self.optimizer)
                torch.nn.utils.clip_grad_norm_(self.model.parameters(), max_norm=1.0)

                # Step optimizer and update GradScaler dynamic scale factor
                self.scaler.step(self.optimizer)
                self.scaler.update()
                self.optimizer.zero_grad()

            if self.interrupted:
                self.save_checkpoint(f"emergency_checkpoint_ep{epoch}_step{step}.pt", epoch, step)
                print("[INFO] Emergency state saved. Exiting gracefully.")
                exit(0)

        return running_loss / len(dataloader)

    def save_checkpoint(self, path, epoch, step=0):
        """Atomic checkpoint saving: writes to temporary file then renames to avoid corruption"""
        temp_path = f"{path}.tmp"
        checkpoint = {
            "epoch": epoch,
            "step": step,
            "model_state": self.model.state_dict(),
            "optimizer_state": self.optimizer.state_dict(),
            "scaler_state": self.scaler.state_dict()
        }
        torch.save(checkpoint, temp_path)
        os.replace(temp_path, path) # Atomic POSIX/Windows filesystem rename
        print(f"[SUCCESS] Atomic checkpoint committed: {path}")

if __name__ == "__main__":
    device = "cuda" if torch.cuda.is_available() else "cpu"
    dummy_model = nn.Sequential(nn.Linear(128, 256), nn.GELU(), nn.Linear(256, 10))
    opt = torch.optim.AdamW(dummy_model.parameters(), lr=1e-3, weight_decay=1e-2)
    loss_fn = nn.CrossEntropyLoss()
    trainer = ProductionTrainer(dummy_model, opt, loss_fn, device=device)
    print(f"Production Trainer initialized successfully on device: {device}")
